# CH9329 应答传输与故障恢复设计

日期：2026-08-04

关联 issue：[#165](http://10.10.10.5:3000/kxn/my_ipkvm/issues/165)

状态：设计已确认，核心实现已完成；真实硬件故障注入和目标 OS 回归待验证。

## 1. 背景

当前项目对 CH9329 使用了两套通信策略：预览探测阶段发送 `GetInfo` 并读取
`0x81` 响应，正式会话阶段由 `SerialCommandQueue` 只写键盘、绝对鼠标和相对鼠标
帧，不消费设备返回的响应。

这使三个状态无法区分：

- 字节是否已经写入主控端串口驱动；
- CH9329 是否收到并处理了命令；
- CH9329 是否返回了成功或错误状态。

当 CH9329 偶发进入无响应状态时，正式会话没有持续读取和关联响应的能力，只能在
串口写失败时感知问题。预览又会重新打开同一个串口，容易产生串口句柄竞争、旧响应
残留和探测结果不可信的问题。

本设计统一预览、desktop 正式会话和 headless 正式会话的 CH9329 传输语义。设计
阶段不修改绝对/相对鼠标报文含义，也不使用复位掩盖鼠标坐标或目标 OS HID 兼容问题。

## 2. 调研结论

### 2.1 当前代码事实

- `crates/ipkvm-core/src/ch9329/frame.rs` 已支持 CH9329 帧构造、解析和校验。
- `crates/ipkvm-core/src/ch9329/decoder.rs` 已支持串口分片、多帧、噪声和坏帧恢复。
- `crates/ipkvm-core/src/ch9329/response.rs` 已解析 `0x81`、`0x82`、`0x84`、
  `0x85` 以及 `0xC1`、`0xC2`、`0xC4`、`0xC5`，尚未解析 Reset 对应的
  `0x8F`、`0xCF`。
- `Ch9329Command` 尚无 `Reset` 命令。
- `CommandQueue::enqueue_batch()` 只表示本地队列接受，不表示设备已经执行。
- `SerialCommandQueue` 直接持有串口，在调用线程同步执行 `write_all()`，没有读线程、
  响应关联、未确认窗口或设备健康状态。
- desktop 预览 adapter 和正式 session factory 会分别打开同一个串口。
- `Ch9329InputSink` 在队列接受后提交本地键鼠状态，因此不能把每个 ACK 的同步等待
  直接塞进 `InputSink` 调用，否则会破坏现有输入泵的吞吐和状态提交边界。

### 2.2 外部实现对比

One-KVM 的 CH9329 实现采用发送后读取响应，并在响应短缺、校验错误或错误状态时
执行 Reset，等待约 2 秒后继续工作。它证明了持续读取响应和故障恢复是可行的参考
模型，但其进程/队列实现不能直接套用到本项目的 Rust `InputSink` 契约。

`kvm-serial` 主要采用只写策略，吞吐和兼容性较简单，但不能发现“串口可写而
CH9329 不再执行”的故障。因此它只能作为输入报文兼容性参考，不能作为本项目正式
传输层的健康监控方案。

CH9329 响应命令没有事务 ID。正常传输下只能按请求发送顺序 FIFO 关联响应；一旦
出现响应错配，后续响应的归属就不再可信，必须把它作为协议传输故障处理。

## 3. 目标与非目标

### 3.1 目标

- 统一预览和正式会话的 CH9329 收发模型。
- 正式会话持续读取、解帧、解析和消费键盘/鼠标响应。
- 不让每个鼠标事件同步等待 ACK。
- 通过有限队列和有限未确认窗口限制设备异常时的输入堆积。
- 在预览无响应时自动执行一次 Reset 和重探测。
- 在正式会话发现设备执行故障时暂停输入、Reset、验证并安全恢复。
- 区分串口链路故障、协议故障和 CH9329 执行故障。
- 为 desktop 和 headless 提供一致的设备健康状态和恢复边界。

### 3.2 非目标

- 不改变 `0x04` 绝对鼠标和 `0x05` 相对鼠标报告的字段语义。
- 不重新设计目标 OS 的绝对/相对 HID 兼容策略。
- 不保证可以人工稳定触发当前偶发的“无响应”故障。
- 不在恢复逻辑中加入固定重试循环或无限自动重连。
- 不要求每个输入事件的调用者等待设备 ACK。

## 4. 方案取舍

### 4.1 每条命令同步等待 ACK

优点是命令结果最直接，容易实现请求-响应配对。

缺点是 9600 波特率下每个鼠标事件都要等待串口往返，连续移动、相对位移拆包、
键盘输入和按钮边沿都会受到阻塞。它还会把传输时序问题直接暴露给同步输入泵，
破坏当前的事件顺序和本地状态提交语义。

不采用。

### 4.2 继续只写，空闲时发送 `GetInfo`

优点是实现简单，输入吞吐较高。

缺点是无法知道具体键盘/鼠标命令是否执行，正式会话仍会遗留未消费响应；如果芯片
处于“串口可写但 HID 不再执行”的状态，故障发现也会延迟到心跳。

不作为正式传输模型，仅保留为明确关闭响应监控时的兼容诊断策略。

### 4.3 单一串口所有者与异步收发

一个传输实例独占串口，调用方提交有界发送队列，工作线程按顺序写入并持续读取
响应。响应按 FIFO 关联到有限 pending 窗口；输入线程不等待单个 ACK，传输线程独立
维护健康状态和恢复状态机。

采用此方案。它保留异步输入吞吐，又让正式会话能够消费响应、发现执行故障并执行
有边界的恢复。

## 5. 总体架构

### 5.1 单一串口所有者

同一串口在任意时刻只能由一个 CH9329 传输实例持有：

- 串口句柄只由传输工作线程使用。
- `Ch9329InputSink` 只持有线程安全的发送端或传输句柄，不直接读写串口。
- 预览探测和正式会话禁止并发打开、并发读取同一个串口。
- 预览成功后关闭探测实例，正式会话再创建正式传输实例。
- 正式传输启动时先完成一次 `GetInfo` 同步屏障，成功后才进入 `Ready`。

### 5.2 命令与响应映射

正式传输层统一消费以下响应：

| 请求命令 | 成功响应 | 错误响应 |
| --- | --- | --- |
| `0x01 GetInfo` | `0x81` | `0xC1` |
| `0x02 Keyboard` | `0x82` | `0xC2` |
| `0x04 MouseAbsolute` | `0x84` | `0xC4` |
| `0x05 MouseRelative` | `0x85` | `0xC5` |
| `0x0F Reset` | `0x8F` | `0xCF` |

成功响应的状态码为 `0x00`。超时、错误状态、坏帧、校验错误、响应命令不匹配和
无法解析的响应都必须进入传输错误统计，并根据当前状态触发恢复或离线处理。

软件 Reset 帧为：

```text
57 AB 00 0F 00 11
```

### 5.3 数据流

```text
InputSink / Probe API
        |
        v
有界发送队列
        |
        v
CH9329 transport worker
   |                |
   | write          | read
   v                v
串口发送       Ch9329Decoder
                    |
                    v
              Ch9329Response
                    |
                    v
              FIFO pending 匹配
                    |
                    v
             健康状态 / 恢复状态机
```

### 5.4 队列与本地状态语义

`enqueue_batch()` 的成功语义保持为“批次已被本地传输层接受”，不改成同步等待
设备执行。设备 ACK 由传输工作线程异步消费。

传输层必须提供：

- 有界发送队列；
- 有限未确认窗口；
- 批次内部顺序保持；
- 不同生产者提交的批次不交错；
- 队列满时可区分拒绝、关闭和设备故障；
- 健康状态、超时、错误响应、复位和重开次数统计。

鼠标移动沿用现有输入调度策略：

- 绝对移动只保留尚未发送的最新坐标；
- 相对移动可以累计或合并，但不能跨越按钮边沿、滚轮、键盘或模式切换；
- 键盘、按钮、滚轮和全释放命令优先于普通移动；
- 恢复期间丢弃尚未发送的普通移动，不能让旧移动在恢复后集中执行。

本地键鼠状态仍在批次被传输层接受后提交。若设备随后报告失败，恢复流程必须先
执行全释放，以重新收敛目标机状态，不能依赖本地状态回滚来假设远端状态已回滚。

## 6. 状态机与故障恢复

### 6.1 传输状态

```text
Opening -> Synchronizing -> Ready
                         |
                         v
                     Recovering
                         |
              +----------+----------+
              |                     |
              v                     v
            Ready                Offline

任意状态的串口打开失败、不可恢复的读写失败 -> Offline
```

`Ready` 状态持续读取响应并处理 pending。仅当空闲期间长时间没有正常响应时，才
发送周期性 `GetInfo` 心跳；正常输入已有 ACK 时不额外发送心跳。

### 6.2 进入 `Recovering`

以下事件触发恢复：

- pending 命令超时；
- 收到对应的错误响应；
- 收到坏帧、校验错误或非法响应；
- 收到与 FIFO 期望命令不匹配的响应；
- 读线程报告设备读取异常。

串口无法打开、串口写入失败或串口读取已经断开属于链路故障。对于无法通信的
链路，不把“发送 Reset”当作有效恢复手段，而是关闭并重新打开串口。

### 6.3 同一串口内的恢复

设备仍可读写时，恢复流程为：

1. 暂停新输入发送。
2. 清理未发送的普通鼠标移动，保留安全释放路径。
3. 发送一次 `Reset`。
4. 等待约 2 秒，让 CH9329 完成复位以及 USB HID 重新枚举。
5. 发送 `GetInfo`，只接受合法的 `0x81` 成功响应。
6. 恢复成功后发送键盘全释放和鼠标按钮全释放。
7. 清理旧 pending，恢复 `Ready` 并继续接受新输入。

Reset 和 GetInfo 是传输屏障，不能与普通输入帧无边界交错。恢复阶段遇到的旧 ACK
不能被误归属到新的普通命令。

### 6.4 重开与离线

Reset 或恢复探测失败时：

1. 停止当前工作线程并关闭串口句柄。
2. 按配置重新打开串口。
3. 清空主控端接收缓冲。
4. 再执行一次 `GetInfo` 同步探测。
5. 成功则创建新的 `Ready` 传输状态，并先发送全释放。
6. 仍失败则进入 `Offline`，通知 desktop/headless 上层停止或隔离输入。

本轮不设计无限自动重连。后续若需要可配置重连次数或退避，应单独扩展状态机和
产品设置，不能由当前恢复流程隐式增加重试。

## 7. 预览探测逻辑

预览连接界面在当前探测会话中执行：

```text
打开串口
  -> 清空接收缓冲
  -> GetInfo
  -> 合法 0x81 成功响应：Ready
  -> 无响应 / 非法响应 / 错误响应
       -> Reset 一次
       -> 等待约 2 秒
       -> GetInfo
       -> 成功：Ready
       -> 失败：显示最终故障原因
```

单次预览操作最多自动发送一次 Reset，刷新或自动波特率扫描不能形成无限复位循环。

自动波特率扫描时，各候选波特率先只发送 `GetInfo`；不能对每个候选波特率都发送
Reset。只有选定的当前探测会话确认设备无响应后，才允许执行这一次 Reset。

以下情况不发送软件 Reset：

- 串口打开失败；
- 串口写入失败；
- 串口句柄已经断开；
- 当前探测会话没有能力把 Reset 帧写入设备。

这些情况直接归类为串口链路故障。

## 8. desktop 与 headless 接入

### 8.1 desktop

- `ProductionProbeBackend` 使用统一的探测解码和一次复位恢复流程。
- 正式 session factory 创建带持续读响应能力的传输实例，不再创建只写队列。
- 连接建立前完成 `GetInfo` 屏障，避免预览成功但正式会话未验证就开始发送输入。
- 传输状态为 `Recovering` 时暂停新的普通输入；为 `Offline` 时通知控制设备离线并
  结束或隔离当前会话。
- 预览探测句柄必须在正式传输创建前释放。

### 8.2 headless

- `build_sink()` 使用与 desktop 相同的传输实现。
- 启动正式输入会话前完成同步探测。
- 现有 `InputSink` 和 `RfbInputPump` 不直接等待 ACK，传输健康由独立传输层维护。
- status/stats 至少暴露：当前在线状态、pending 数量、超时数、错误响应数、协议
  错误数、Reset 次数、串口重开次数和被丢弃的普通移动数量。

## 9. 自动化测试

### 9.1 协议与解码

- `Reset` 命令生成金样帧 `57 AB 00 0F 00 11`。
- 解析 `0x8F` 成功响应和 `0xCF` 错误响应。
- 覆盖 `0x82`、`0x84`、`0x85` 成功/错误响应。
- 覆盖串口分片、多帧、噪声、坏校验和非法响应。

### 9.2 传输与 FIFO

- 正常命令按照发送顺序匹配 ACK。
- 响应错配会进入协议故障，不会静默推进 pending。
- pending 窗口和发送队列有界。
- 队列满时普通移动可合并或丢弃，键盘、按钮、滚轮和释放路径保持顺序。
- 传输线程持续消费响应，接收缓冲不会因正式会话只写而堆积。
- 串口读失败、写失败、超时和错误状态分别映射为可观察的错误类别。

### 9.3 恢复状态机

- 预览无响应时只执行一次 Reset，随后重探测成功和失败分别覆盖。
- 正式会话命令超时、错误响应、坏帧和响应错配都能进入恢复。
- Reset 后必须等待，再执行 GetInfo 验证。
- 恢复成功后先发全键盘/鼠标释放，再恢复输入。
- 恢复失败后重开串口，最终进入 Offline。
- 预览实例和正式实例不能同时读取同一串口。

### 9.4 输入回归

- 不因 ACK 等待阻塞输入调用线程。
- 鼠标移动合并不跨越按钮边沿、滚轮、键盘和模式切换。
- 拖拽和键盘状态的发送顺序保持现有 #151、#154、#156 决议。
- 传输故障恢复后不存在卡键或卡鼠标按钮的本地状态假设。

## 10. 人工验证边界

CI 没有独占的 CH9329、USB 转串口、USB HID 目标机和可控的芯片故障注入环境，
因此以下项目必须使用真实硬件验证：

- 正常情况下 `0x82`、`0x84`、`0x85` 响应是否持续返回；
- 9600 波特率下键盘、点击、拖拽、绝对移动和相对移动的吞吐与延迟；
- 正常 Reset、等待、GetInfo 和全释放序列；
- USB HID 重新枚举期间目标机是否保持无卡键、无卡按钮。

当前“串口无应答”属于偶发问题，无法稳定人工触发。因此不能把“人工成功制造无
响应并完成自动恢复”作为验收前提，也不能用一次未复现来证明恢复逻辑正确。自动化
测试必须通过 fake serial 确定性注入超时、坏帧、错误响应和读写失败；真实硬件只需
在自然发生无响应时记录日志和恢复结果。实现完成后，人工记录应包含硬件型号、
串口参数、目标 OS、实际发生的故障现象和恢复结果；若测试期间未自然发生故障，
必须明确记录“未复现”，不能填写为“恢复通过”。

## 11. 实施分层

实现按以下顺序拆分：

1. `ipkvm-core`：增加 Reset 命令、响应解析、传输抽象、读写工作线程、FIFO pending、
   有界队列和恢复状态机。
2. `ipkvm-core` fake serial：提供可控的 ACK、超时、坏帧、错误响应、读写失败和
   设备重新上线场景。
3. desktop adapter：让预览复用统一探测/恢复能力，让正式 session 使用统一传输实例。
4. headless adapter：接入统一传输、状态上报和会话离线通知。
5. 文档与运行状态：更新协议设计、串口说明、预览状态和故障恢复说明。

每一层都必须保留已有绝对/相对输入语义，不把传输恢复与鼠标坐标、OS profile 或
Pointer Lock 逻辑混合实现。

- `SerialCommandQueue` 改为单一串口 worker，持续读取响应并按 FIFO 关联 pending；
