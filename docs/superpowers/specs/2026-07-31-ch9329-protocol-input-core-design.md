# CH9329 协议与输入核心设计

日期：2026-07-31

关联 issue：`#1`

## 目标

在真实硬件到货前，完成一个可由自动化测试充分验证的 CH9329 协议与输入核心，为桌面版、RFB/VNC 和网页入口提供唯一的键鼠状态实现。

本阶段交付：

- CH9329 命令帧编码、应答帧解析和串口字节流解帧。
- 普通键盘 6KRO 状态、8 个修饰键、重复事件去重和强制释放。
- 绝对鼠标、相对鼠标、按钮和滚轮状态。
- 有序批量命令提交接口和 fake 实现。
- 厂家示例、kvm-serial 已使用帧和状态机性质的自动化测试。

本阶段不交付：

- 真实串口枚举、打开、读写和重连。
- CH9329 自动探测、自动改波特率和心跳。
- 桌面窗口、RFB、Web 和视频采集接入。
- 文本粘贴转模拟键入。
- 非 `en_US` 键盘布局。
- 真实硬件兼容性结论。

## 证据与边界

设计以两类证据为基础：

- WCH 协议文档是帧格式、命令码、应答状态和字段范围的规范来源。
- kvm-serial 提交 `4d921999539e6734df03c031874db197718fb7b8` 是已经用于真实设备的兼容性参考，用于判断最小可工作行为，但不覆盖其未实现的协议能力：
  `https://github.com/sjmf/kvm-serial/tree/4d921999539e6734df03c031874db197718fb7b8`

kvm-serial 的 CH9329 路径采用以下行为：

- 默认以 9600 波特率打开串口。
- 打开后直接发送键盘和鼠标命令，不需要启动握手。
- 只写串口，不读取命令应答。
- 绝对坐标使用 `floor(4096 * coordinate / extent)`。
- 相对位移限制到 `-127..127`。
- 鼠标移动使用绝对报告，按钮和滚轮使用零位移相对报告。

这些行为证明“9600 波特率、协议模式 0、直接写帧”适合作为硬件到货后的兼容基线，但不能证明以下做法是正确的长期实现：

- 忽略所有应答。
- 允许超过协议规定 64 字节的数据区。
- 丢弃超过单帧范围的相对位移。
- 不维护普通键多键状态。
- 失焦时不强制释放。

## 核心决策

### 纯状态与真实传输分离

输入核心只负责：

1. 校验输入事件。
2. 计算下一状态。
3. 生成一个有序 `CommandBatch`。
4. 在整批命令被队列接受后提交下一状态。

“队列接受成功”只表示命令已进入本进程的有序发送队列，不表示 CH9329 已执行命令。真实传输层以后负责写串口、读取应答、超时、重试和设备健康状态。

这样可以同时支持两种硬件策略，而不改变桌面、RFB 和 Web 输入接口：

- 兼容发送策略：按顺序写帧，不等待每条命令应答，行为接近 kvm-serial。
- 应答监控策略：读取并校验应答，维护设备状态；是否逐命令等待由硬件验证决定。

本阶段只建立两种策略都能使用的协议和队列边界，不实现真实策略。

### 文本输入与物理输入分离

`type_text()` 不属于底层物理输入状态机。文本粘贴需要键盘布局、锁定键状态、字符节流和失败恢复，应由后续独立的文本键入服务实现。

当前 `InputSink` 移除 `type_text()`；后续如需要，增加独立 `TextInput` 接口。这样物理键盘、RFB `KeyEvent` 和文本粘贴不会共享含义不清的同步方法。

### 默认波特率保持 9600

WCH 数据手册和 kvm-serial 都以 9600 作为出厂默认值。硬件到货前不把 115200 作为默认值，也不实现自动改写芯片参数。

硬件到货后允许手动选择其他波特率，并通过诊断工具验证：

- 成品线的实际默认值。
- 设备供电电压和 115200 支持情况。
- 参数修改是否需要控制 `SET` 引脚。
- 改写参数后是否必须重新上电。

## CH9329 协议模型

### 帧

命令和应答共用以下格式：

```text
57 AB | ADDR | CMD | LEN | DATA... | SUM
```

约束：

- 帧头固定为 `0x57 0xAB`。
- `DATA` 长度范围为 `0..=64`。
- `SUM` 是此前所有字节的 8 位回绕累加和。
- 普通命令码范围是 `0x01..=0x3f`。
- 正常应答命令码是原命令码按位或 `0x80`。
- 异常应答命令码是原命令码按位或 `0xc0`。

`Ch9329Frame::new()` 拒绝超过 64 字节的数据。`Ch9329Frame::parse()` 校验最小长度、帧头、声明长度、数据上限和校验和。

### 增量解帧

串口读取可能在任意字节位置分片，也可能一次返回多帧。`Ch9329Decoder` 维护有限缓冲区并提供：

```text
push(bytes) -> Vec<Result<Ch9329Frame, Ch9329DecodeError>>
```

规则：

- 保留不完整帧，等待后续字节。
- 一次输入可以产出零帧、一帧或多帧。
- 帧头前的噪声被丢弃，并产生可统计的同步丢失错误。
- 长度超过 64、校验失败或非法帧不会阻塞后续合法帧解析。
- 缓冲区设置固定上限，连续垃圾数据不能造成无界内存增长。

### 类型化命令与应答

本阶段支持：

- `GetInfo`：命令 `0x01`。
- `Keyboard`：命令 `0x02`，固定 8 字节报告。
- `MouseAbsolute`：命令 `0x04`，固定 7 字节报告。
- `MouseRelative`：命令 `0x05`，固定 5 字节报告。

`GetInfo` 正常应答解析为：

- 芯片版本。
- USB 是否枚举成功。
- Num Lock、Caps Lock、Scroll Lock LED 状态。
- 保留字节。

状态应答支持厂家定义的 `0x00`、`0xe1..=0xe6`。未知状态码被保留为 `Unknown(u8)`，不能因固件新增状态而导致解帧失败。

## 键盘状态

键盘报告固定为：

```text
modifier | 00 | key0 | key1 | key2 | key3 | key4 | key5
```

状态机维护：

- 8 位修饰键掩码。
- 最多 6 个互不重复的普通键。
- 普通键按下顺序。

行为：

- 修饰键使用 HID usage `0xe0..=0xe7`，映射到 modifier bit，不占普通键槽位。
- 已按下键再次按下时不改变状态，也不产生命令。
- 未按下键收到释放时不改变状态，也不产生命令。
- 第 7 个普通键按下返回 `RolloverLimitExceeded`，原状态保持不变。
- 普通键释放后压紧剩余槽位，但保留其相对按下顺序。
- `release_all()` 无论本地状态是否为空都发送全零键盘报告，以修复可能存在的本地和目标机状态偏差。
- 自动重复由上层显式建模；重复 `Down` 不能隐式充当自动重复。

输入 usage 属于 USB HID Keyboard/Keypad 页。`0x00..=0x03` 等保留或错误 usage 被拒绝，错误中保留原值。

## 鼠标状态

状态机维护：

- 当前模式：绝对或相对。
- 左、右、中键的当前位掩码。
- 最近一次合法绝对坐标及对应帧缓冲尺寸。

### 绝对坐标

输入坐标必须满足：

```text
width > 0
height > 0
0 <= x < width
0 <= y < height
```

映射遵循厂家示例和 kvm-serial：

```text
mapped = floor(4096 * coordinate / extent)
```

合法输入的输出范围始终为 `0..=4095`。视频区域外的坐标由桌面或 RFB 适配层过滤；核心不采用 kvm-serial 面向多显示器全局坐标的负数回绕。

绝对模式下：

- 移动报告携带当前按钮状态。
- 按钮和滚轮报告使用最近一次绝对坐标。
- 尚无绝对坐标时收到按钮或滚轮事件，返回 `PointerPositionUnknown`。

### 相对位移

CH9329 单帧相对字段范围采用 `-127..=127`。超过单帧范围的 `dx`、`dy` 或滚轮齿数被拆成最少数量的连续报告，每个字段之和等于原始输入。

例如：

```text
dx = 200  -> 127, 73
dy = -200 -> -127, -73
```

这样不会采用 kvm-serial 的截断策略丢失移动距离。

滚轮事件在核心中使用“齿数”语义。Windows 的 `WHEEL_DELTA=120`、Qt angle delta、浏览器 delta mode 等平台单位必须在各入口适配层归一化后再进入核心。

### 按钮、模式切换和释放

- 按钮按下设置对应位，释放只清除对应位，其他按钮保持不变。
- 重复按钮事件不产生命令。
- 模式切换时如果有按钮处于按下状态，先在旧模式发送释放报告，再清空按钮状态并切换。
- `release_all()` 总是发送全零键盘报告和鼠标按钮释放报告，以修复本地状态与目标机可能存在的偏差。
- 绝对模式已有最近坐标时，鼠标释放使用该绝对坐标；尚无绝对坐标时，使用零位移相对报告释放按钮，但不改变当前模式。

## 有序命令批次

键盘和鼠标可能产生一帧或多帧。核心使用 `CommandBatch` 保证一次输入转换产生的帧不可被其他入口插入。

队列接口提供：

```text
enqueue_batch(batch) -> Result
stats() -> QueueStats
```

契约：

- 一个批次要么整体被队列接受，要么整体被拒绝。
- 批次内部顺序必须保持。
- 多个生产者提交的批次不能交错。
- 返回成功只表示已接受，不表示串口已写完或设备已应答。
- fake 队列可以配置“下一批失败”，用于验证失败时输入状态不提交。

## 错误与恢复

错误按层次区分：

- 协议构造错误：字段长度、非法 usage、非法坐标。
- 解帧错误：噪声、非法长度、校验失败、不完整帧。
- 输入状态错误：6KRO 溢出、绝对位置未知。
- 队列错误：队列关闭、容量耗尽。
- 设备执行错误：应答超时或设备返回错误状态，留给真实传输层。

输入核心在批次提交失败时不提交下一状态。真实传输断开后，重连流程必须先发送强制释放批次，再接受新的控制输入。

### 参考模型与金样转录（2026-08-01 补充）

为保证“没有真实硬件也能证明状态机准确”，在 `ch9329/input.rs` 测试中新增
独立参考模型，不调用生产 `KeyboardState`/`MouseState` 的任何方法：

- `KeyboardModel` 只维护“修饰键位 + 普通键集合”，按协议语义推导每一批事件
  应产生的报告；生产实现按按下顺序填槽，因此断言使用集合相等，不约束槽位
  排列顺序。
- `PointerModel` 独立实现绝对坐标换算（`floor(4096 * coordinate / extent)`）、
  相对位移拆包、按钮掩码和滚轮命令序列，逐帧对比生产输出。
- 随机事件序列同时注入 `FakeCommandQueue` 失败，断言入队失败时状态回滚、
  不产生部分帧。
- 新增“混合输入金样转录”测试：键盘 + 修饰键 + 绝对鼠标 + 按钮 + `release_all`
  的完整字节序列与协议金样逐字节对比，并断言 `QueueStats` 计数。

这些测试实际发现并修复了一个真实边界：同一批 `[释放 K, 按下 K]` 按键集合
不变但槽位顺序变化时，旧实现会多发一帧键盘报告。修复为按“修饰键 + 按键集合”
做语义比较，集合不变时不入队；回归测试为
`batch_that_only_reorders_slots_does_not_enqueue`。

proptest 保存的失败种子位于 `crates/ipkvm-core/proptest-regressions/`，按
proptest 惯例提交到版本库，确保历史失败用例持续回归。

## 真实硬件实测（2026-08-02 补充）

硬件到货（CH9329 模组 + CH340 成品线，主控端 COM9 → 目标端 ARM 10.10.10.21，目标端 `evtest /dev/input/event6` 观测）后，对本设计的关键假设做了闭环验证。结论修正/固化了上文的若干推断。

### 实测链路与观测方式

- 主控端：Windows COM9（CH340，9600 8N1），通过 `ipkvm-core` 的 `ch9329_probe` 示例逐帧发送。
- 目标端：ARM 上 CH9329 模组以 USB 枚举为「WCH UART TO KB-MS_V1.8」（VID 1A86），键鼠作为两个 HID 设备出现；鼠标在 `/dev/input/event6`（支持 ABS_X/Y 0–4095 与 BTN_*），用 `evtest` 记录事件。

### 实测结论

1. **绝对帧（CMD 0x04）只识别坐标，按钮位不被目标机识别。**
   - 对 0x04 帧携带 buttons=1（左）、2（右）、4（中）、7（全按），目标端**只产生 ABS_X/ABS_Y 事件，无任何 BTN_* 事件**。
   - 因此生产代码「鼠标按键始终走相对帧（0x05）」的修正（见「鼠标状态」一节）**成立且有实测依据**：绝对帧的按钮位是无操作，按键必须用零位移相对帧发送。
   - 附带影响：kvm-serial 的 `on_move` 把当前按钮位放进绝对帧（以为拖动能保留按钮）实际是无操作；按钮状态由芯片在绝对帧之间保持不变，所以其拖拽仍碰巧正确。**我们选择「绝对帧只携带坐标、按钮仅走相对帧」更诚实且不依赖芯片的隐式保持。**

2. **拖拽时按钮状态在绝对移动帧之间保持。**
   - 实测序列：绝对移动 A → 左键按下（相对帧）→ 绝对移动 B → 左键释放（相对帧），在绝对移动 B 期间**没有出现意外的 BTN_LEFT up**，拖拽完整。
   - 说明即使绝对移动帧不携带按钮位，芯片也保持此前相对帧设置的按钮状态，不打断拖动。

3. **CH9329 绝对指针的初始位置为 2048,2048（12-bit 空间中心）。**
   - 向 (2048,2048) 发绝对帧**不产生任何 ABS 事件**（位置未变化），曾一度被误判为「绝对帧无响应」。诊断时需注意：若目标端指针已在中心，测试绝对移动请避开 (2048,2048)。

4. **相对帧（0x05）按钮与移动均有效。**
   - 零位移相对帧产生正确的 BTN_* press/release；相对移动产生 REL_X/REL_Y，幅度与拆分逻辑一致。

5. **键盘注入可用。**
   - `ch9329_probe text hello` 在目标端控制台出现 `hello`（见示例注释），证明键盘 0x02 帧、6KRO 报告与 9600 波特率基线正确。

### 对设计的落定影响

- 「鼠标状态」一节中「绝对坐标使用绝对帧、按钮与滚轮使用零位移相对帧」是**实测确认的兼容基线**，不再是推断。
- 修正了本设计此前「绝对帧按钮位由芯片处理」的隐含假设：绝对帧的按钮位是无效字段，不应依赖。
- 保留的未知：芯片模式切换、`GetInfo` 应答、锁定键 LED、115200 行为仍按「诊断顺序」待后续独立验证。
