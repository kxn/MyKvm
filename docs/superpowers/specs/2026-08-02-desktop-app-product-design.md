# 桌面 app 产品与交互设计

- 关联 issue：#33
- 日期：2026-08-02
- 状态：第一版已实施（2026-08-02）；设计稿已纳入 `sjmf/kvm-serial` UI 复核结论

## 背景

桌面版是给本机操作者使用的 KVM 客户端。用户关心的是选对采集画面、选对控制设备、连接后稳定控制目标机；不应该在主流程里理解波特率、像素格式、RFB 或输入泵这些内部细节。

第一版桌面 app 不做远程服务，不绑定网络端口，不做鉴权。它直接使用本机视频采集设备和本机 CH9329 控制设备。headless 已经完成运行时设备选择；desktop 要复用相同的会话级重连思路，但产品界面必须更像普通 KVM/VNC 工具。

## 产品目标

- 启动后让用户明确选择视频设备和控制设备，而不是依赖命令行或自动连接上次设备。
- 用户选中视频设备后能看到静图预览，确认这就是目标机画面。
- 用户选中控制设备后能看到 CH9329 探测结果，避免向错误串口发送数据。
- 只有视频预览可用且控制设备合法时才允许连接。
- 连接后提供可呼出的控制菜单，用于特殊按键、释放输入、截图和重新选择设备。
- 控制台保持画面优先，只用状态栏和可呼出菜单承载运行信息与操作。
- 目标机重启、视频断流、分辨率变化、CH9329 掉电/恢复时，desktop 和 headless 都不能崩溃或卡死。

## 非目标

- 不提供强制连接非法控制设备的入口。
- 不在主流程展示波特率、视频格式策略、像素格式、RFB 参数等技术项。
- 不做自动恢复上次设备并连接。
- 不做公网访问、HTTP 控制台、TLS、token 或多用户权限。
- 不做无缝设备热替换；切换设备采用会话级重连。

## 参考项目借鉴

本设计复核了 GitHub 项目 `sjmf/kvm-serial` 的桌面 UI。可采纳的产品结论如下：

- 连接后的控制台应以视频画面为中心，避免常驻设置面板挤占画面。
- 菜单适合承载低频操作，例如截图、粘贴文本、特殊键、视频缩放和高级设置。
- 底部状态栏适合持续显示串口、键盘、鼠标坐标和视频信息，便于运行中排查。
- 截图应先复制到剪贴板，再允许用户保存为文件。
- 视频缩放至少需要“适配窗口”“1:1”和“调整窗口到视频尺寸”。

不采纳的部分：

- 不把首次设备选择藏在菜单里；本 app 启动后仍先进设备选择 dialog。
- 不自动打开默认串口作为有效控制设备；必须先通过 CH9329 探测。
- 不把波特率、协议、分辨率等技术项暴露在主流程。

## 启动与设备选择

app 启动后显示设备选择 dialog。第一屏只包含用户能直接理解的内容：

- 视频设备。
- 控制设备。
- 刷新检测。
- 连接。
- 高级。

“高级”中可以放波特率、视频格式策略、鼠标模式等配置，但不能放绕过 CH9329 探测的强制连接开关。默认配置应覆盖普通 USB 设备场景，用户不需要先进入高级设置才能使用。

不自动连接上次设备。后续可以记住上次选择并预选列表项，但仍由用户确认并点击连接。

## 视频设备检测

用户选中视频设备后，app 立即尝试打开该设备并抓取一帧静图预览。

预览区域有以下状态：

- 未选择：提示选择视频设备。
- 检测中：显示正在获取预览。
- 可用：显示最近一次成功抓取的静图，标出设备名和分辨率。
- 无信号：设备可打开，但暂时没有有效帧。
- 打开失败：设备被占用、驱动错误或权限错误。
- 已断开：原设备从系统枚举中消失。

预览检测只用于连接前确认设备，不启动正式控制会话。正式连接时仍按当前选择创建会话。若预览占用独占设备，进入正式连接前必须释放预览句柄，再创建正式会话。

## 控制设备检测

用户选中控制设备后，app 打开串口候选并执行 CH9329 探测。探测应使用协议中的读信息能力；没有合法回包不能视为 CH9329。

控制设备区域有以下状态：

- 未选择：提示选择控制设备。
- 检测中：显示正在验证控制设备。
- 可用：显示 CH9329 已识别。
- 不是合法控制设备：串口可打开，但回包不符合 CH9329。
- 无响应：串口可打开，但探测超时。
- 打开失败：串口被占用、权限错误或驱动错误。
- 已断开：原设备从系统枚举中消失。

连接按钮只有在视频状态为“可用”且控制设备状态为“可用”时启用。不允许强制连接探测失败的控制设备。

## 刷新检测

设备选择 dialog 提供一个统一的“刷新检测”按钮。

点击后：

- 重新枚举视频设备和串口设备。
- 对当前选中的视频设备重新抓取预览帧。
- 对当前选中的控制设备重新执行 CH9329 探测。
- 保留仍然存在的当前选择；若设备消失，则显示“已断开”并禁用连接。

刷新检测用于硬件刚插入、目标机刚上电、驱动恢复或设备状态刚变化后的手动重检。用户不需要分别刷新视频和控制设备。

## 连接与控制台视图

点击连接后，app 进入控制台视图：

- 主区域显示视频画面，保持比例，不拉伸变形。
- 无帧时显示“无信号”，保留当前会话状态。
- 底部状态栏分四段显示：控制设备状态、键盘输入状态、鼠标坐标、视频状态。
- 视频区域获得焦点后才发送键盘和鼠标输入。
- 视频区域失焦、停止连接、重新选择设备或退出 app 时，必须先释放所有按键和鼠标按钮。
- 窗口缩放时按显示区域和 DPI 重新计算坐标。
- 视频分辨率变化时，立即更新显示比例和坐标换算。

切换设备不退出 app。用户从控制菜单进入“重新选择设备”，dialog 打开后可以重新检测并连接。确认新设备后，内部流程是释放输入、停止旧会话、释放旧硬件、创建新会话。

## 控制菜单

控制台内提供一个可呼出的菜单，行为接近 VNC/KVM 客户端工具栏。菜单不应长期遮挡画面，默认收起，用户通过按钮或快捷入口打开。

第一版菜单包含：

- 发送特殊键。
- 粘贴文本。
- 释放所有按键。
- 截图。
- 重新选择设备。
- 停止连接。
- 高级设置。

特殊键至少覆盖：

- Ctrl+Alt+Del。
- Esc。
- F1 到 F12。
- Insert、Delete、Home、End、PageUp、PageDown。
- 方向键。

这些按键通过菜单发送，是因为主控系统可能拦截 Alt+Tab、Win、Ctrl+Alt+Del 等组合，不能只依赖本地键盘事件捕获。

粘贴文本从本机剪贴板读取文本，按字符转换为目标机键盘输入。发送过程中菜单项应临时禁用，避免重复触发；遇到无法映射的字符时跳过或报告，不应卡住整个输入路径。

截图行为采用两段式：先把当前视频帧复制到本机剪贴板，再弹出保存入口。用户取消保存时，截图仍保留在剪贴板。无有效视频帧时，菜单动作给出明确提示。

视频缩放放入菜单或高级视图，第一版至少包含：

- 适配窗口。
- 1:1 显示。
- 调整窗口到视频尺寸。

## 硬件异常与恢复

真实硬件到货后，目标机重启会暴露三个恢复场景：视频断流、分辨率变化、CH9329 因目标机供电变化而掉线/恢复。这些是产品要求，不是测试例外。

### 视频断流

视频设备仍存在但暂时没有帧时：

- desktop 显示“无信号”，不关闭 app。
- 会话保持存在，用户可以停止或重新选择设备。
- 恢复出帧后自动回到画面显示。
- headless 的 `/api/status` 应反映无新帧或断流状态，RFB 服务不应崩溃。

### 分辨率变化

视频恢复后分辨率可能变化。desktop 必须更新显示比例和输入坐标。headless 必须继续通过 RFB `DesktopSize` 通知客户端，不要求用户重启 headless 进程。

### 控制设备掉线

CH9329 掉电或串口短暂不可用时：

- 输入路径进入“控制设备离线”状态。
- app 显示控制设备离线，暂时不发送输入。
- 恢复后重新执行 CH9329 探测；确认合法后恢复输入。
- 失去控制设备时不能保留软件侧“按键仍按下”的危险状态，应尽力调用释放逻辑，并在恢复后以空输入状态继续。
- headless 也需要同样的串口离线/恢复模型。

> 拆分记录：desktop 第一版已实现 UI 侧「无信号/断流」显示、分辨率变化重建和「控制设备离线 + 手动刷新恢复」；headless 的视频断流与 CH9329 掉线自动恢复模型拆为独立 issue #37 跟踪，不在本 PR 中声明完成。

## 架构边界

desktop 不依赖 headless，不走本机 HTTP 或 RFB 回环。它直接使用共享库：

- `ipkvm-video`：枚举视频设备、预览抓帧、正式视频帧源。
- `ipkvm-session`：会话生命周期、输入泵、RFB 输入事件模型、连接状态统计。
- `ipkvm-core`：CH9329 输入 sink、串口命令、输入抽象。

为了避免把 UI 和硬件生命周期混在一起，desktop 需要把代码拆成以下边界：

- 设备检测服务：负责枚举、视频预览、CH9329 探测和刷新检测。
- 会话控制器：负责连接、停止、设备切换和硬件恢复状态。
- 渲染视图：负责视频画面、无信号状态和缩放坐标。
- 输入适配器：负责把窗口键鼠事件转换为共享输入事件。
- 控制菜单：负责特殊键、截图、释放输入和重新选择设备。
- 状态栏：负责汇总控制设备、键盘输入、鼠标坐标和视频状态。

第一版可以在实现上保持简单，但边界必须清楚，避免把整个 app 写成一个不可维护的巨型事件循环。

## Headless 共享要求

本设计新增的硬件恢复要求同时适用于 headless：

- 视频断流不能导致进程退出或 RFB 服务不可用。
- 分辨率变化继续使用现有 `DesktopSize` 路径通知客户端。
- CH9329 掉线后输入路径进入离线状态，恢复后重新探测并恢复输入。
- `/api/status` 应能表达视频和控制设备的在线/离线/错误状态。
- `/api/session` 的会话级重启仍是换设备路径，不替代硬件短暂异常恢复。

如果这些能力超出 #33 的实现范围，后续应拆出独立 issue，但产品要求在本设计中先固定。

## 测试策略

自动化测试优先覆盖状态机和边界：

- 视频检测：未选择、检测中、预览成功、无信号、打开失败、已断开。
- 控制检测：未选择、检测中、CH9329 合法、非 CH9329、无响应、打开失败、已断开。
- 连接按钮：只有视频可用且控制设备合法时启用。
- 刷新检测：同时刷新设备枚举、视频预览和 CH9329 探测结果。
- 会话切换：重新选择设备时释放输入、停止旧会话、释放旧硬件、启动新会话。
- 输入安全：失焦、停止、切设备、退出时调用释放逻辑。
- 粘贴文本：发送期间禁用重复触发，完成或失败后恢复。
- 截图：有帧时复制到剪贴板并可保存；无帧时给出提示。
- 状态栏：控制设备、键盘输入、鼠标坐标和视频状态随会话变化更新。
- 分辨率变化：显示比例和坐标换算更新。
- headless 回归：视频断流、分辨率变化和控制设备离线不会让传输层崩溃。

人工验证用于真实窗口和真实硬件：

- 启动 app，选择采集卡，确认静图预览。
- 选择非 CH9329 串口，确认连接按钮禁用。
- 选择 CH9329，确认探测合法后连接按钮启用。
- 连接后发送普通键鼠和特殊键。
- 使用粘贴文本，确认目标机收到文本且发送期间不会重复触发。
- 截图，确认图片先进入剪贴板，并可另存为文件。
- 被控机重启，确认视频断流、恢复和分辨率变化能正常处理。
- 断开/恢复 CH9329 供电，确认 app 状态与输入恢复。

## 验收标准

- 用户无需命令行即可选择视频设备和控制设备。
- 视频设备选中后有预览；预览失败有明确状态。
- 控制设备必须通过 CH9329 探测；失败时不能连接。
- “刷新检测”能统一更新视频和控制设备检测结果。
- 控制台视图以视频画面为中心，底部状态栏显示控制设备、键盘、鼠标和视频状态。
- 控制台视图提供可呼出的菜单，并能发送特殊键、粘贴文本、释放输入和截图。
- 截图先复制到剪贴板，并允许用户保存为文件。
- 重新选择设备不退出 app，采用会话级重连。
- 被控机重启相关的断流、分辨率变化和控制设备离线场景有明确处理路径。
- 设计不引入强制连接非法串口、默认自动连接上次设备或主流程技术参数堆叠。
