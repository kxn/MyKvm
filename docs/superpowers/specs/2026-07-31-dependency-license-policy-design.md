# 依赖许可证白名单与本地自动审计设计

状态：已批准，待实施

关联 issue：#13

## 1. 背景

项目即将引入 WebSocket/noVNC、串口、视频采集和桌面 GUI 相关依赖。现有粗粒度设计只记录了许可证原则，没有机器可执行的依赖准入规则，也无法在本地统一验证中阻止以下变化：

- 新增未审查许可证的 Cargo 依赖。
- 从未知注册表或 Git 仓库引入依赖。
- Git 依赖没有锁定到不可变提交。
- 依赖升级后许可证表达式或来源发生变化。
- 把 Rust 依赖审计误当成 noVNC、系统动态库等非 Cargo 组件的完整合规审计。

本项目已经明确接受 LGPL 的合规使用，但 Rust 普通依赖通常静态链接进最终二进制，满足 LGPL 的重新链接、源码和许可证提供义务比动态库复杂。因此 LGPL 和 MPL 等弱 copyleft 许可证不能作为全局无条件白名单，必须按具体依赖记录使用和分发方式。

## 2. 目标

本项完成以下闭环：

1. 固定许可证审计工具和版本。
2. 建立 Rust 依赖的机器可执行许可证白名单。
3. 默认拒绝未知注册表和未审批 Git 依赖。
4. 为条件接受许可证建立按包例外流程。
5. 把许可证和来源检查接入 `scripts/verify.ps1`。
6. 用自动化负向测试证明不允许的许可证和 Git 来源确实会失败。
7. 用中文长期文档说明 Cargo 审计的能力边界，以及 noVNC、系统库、动态库和静态资源的额外审查要求。

## 3. 不做范围

本项不实现：

- Gitea Actions 或远端 runner。
- WebSocket、HTTP、noVNC、串口、视频或 GUI 运行时依赖。
- 安全漏洞、废弃依赖或供应链恶意行为的阻塞门禁。
- 发布包的完整第三方许可证清单生成。
- 对法律义务作最终法律意见。

安全漏洞审计以后独立设计。本项只执行 `licenses` 和 `sources` 两类确定性检查，避免本地完整验证受在线漏洞数据库更新影响。

## 4. 调研结论

### 4.1 工具版本

采用 `cargo-deny 0.20.2`，并在本地脚本中精确校验版本。

选择依据：

- crates.io 显示 `0.20.2` 的最低 Rust 版本是 `1.88.0`，兼容项目固定的 Rust `1.89`。
- `cargo-deny` 原生解析 SPDX 表达式。
- `licenses.exceptions` 可以把弱 copyleft 或其他条件许可证限制到具体包，而不是放宽整个依赖图。
- `sources` 检查可以默认拒绝未知注册表和 Git 来源。
- 工具能直接检查 Cargo 实际解析出的完整依赖图，不需要项目自行重写 Cargo 和 SPDX 语义。

本地安装命令固定为：

```powershell
cargo install --locked --version 0.20.2 cargo-deny
```

验证脚本不自动安装工具。自动安装会产生隐式网络访问、耗时和全局环境修改，不适合作为每次验证的副作用。

### 4.2 备选方案

#### 方案 A：cargo-deny 门禁加中文策略文档

优点：

- SPDX、依赖图和来源规则由成熟工具处理。
- 可直接对具体 crate 建立例外。
- 能接入当前本地验证入口。
- 后续引入 axum、tokio-tungstenite 和桌面依赖时复用同一规则。

缺点：

- 开发机需要安装固定版本的额外 Cargo 工具。
- Cargo 之外的 JavaScript、动态库和静态资源仍需单独审查。

#### 方案 B：自行解析 cargo metadata

优点：

- 不需要额外命令行工具。

缺点：

- 必须自行实现 SPDX 表达式、许可证文件推断、目标依赖图和来源规范化。
- 容易出现“脚本看似通过但法律表达式判断错误”的根因风险。
- 后续维护成本高。

#### 方案 C：只生成第三方许可证报告

优点：

- 适合发布阶段生成归属清单。

缺点：

- 报告工具不能作为准入门禁。
- 无法证明未批准许可证或来源会让开发验证失败。

采用方案 A。发布报告生成留到发布打包阶段，不能替代当前门禁。

## 5. 许可证分级

### 5.1 全局自动允许

以下许可证可以进入 `deny.toml` 的全局允许列表：

- `MIT`
- `Apache-2.0`
- `Apache-2.0 WITH LLVM-exception`
- `BSD-2-Clause`
- `BSD-3-Clause`
- `ISC`
- `Zlib`
- `Unicode-3.0`

允许列表保持最小化。某个许可证“通常宽松”不是预先加入列表的充分理由；只有实际依赖需要且完成审查后才增加。

对于 `A OR B`，只要项目可以选择一个已允许许可证，检查可以通过。对于 `A AND B`，所有组成许可证都必须允许或有具体包例外。

### 5.2 条件接受

以下类型可以接受，但不得直接加入全局允许列表：

- `MPL-2.0`
- `LGPL-2.1-only`、`LGPL-2.1-or-later`
- `LGPL-3.0-only`、`LGPL-3.0-or-later`
- 需要额外归属、源码、可替换或重新链接安排的其他许可证。

Cargo 依赖需要在 `licenses.exceptions` 中按 crate 和必要的版本范围批准，并在中文策略文档中记录：

1. 依赖名称和版本范围。
2. 引入目的。
3. 实际链接或进程隔离方式。
4. 发布时必须附带的许可证、源码、对象文件或替换说明。
5. 升级后需要重新审查的条件。

noVNC 不属于 Cargo 依赖。其 MPL-2.0 核心和其他静态资源许可证必须在资源锁定 issue 中单独记录版本、原文件、修改范围和发布归属。

### 5.3 默认拒绝

以下情况默认失败：

- 不在全局允许列表且没有具体包例外的许可证。
- 无法确定许可证。
- 自定义许可证或非 SPDX 表达式，除非有基于固定许可证文件哈希的澄清。
- GPL、AGPL、SSPL、商业专有或限制用途许可证，除非未来有明确的项目级重新授权决策。

这不是声称所有被拒绝许可证都不可用，而是要求变更先经过独立设计和审查，不能随普通依赖更新进入主分支。

## 6. 依赖来源策略

默认规则：

- 只允许 crates.io 官方注册表。
- 未知注册表失败。
- 所有 Git 来源默认失败。
- 路径依赖允许，用于当前 workspace 和自动化测试夹具。

未来确需 Git 依赖时：

1. 开 issue 说明 crates.io 版本为什么不可用。
2. 审查仓库归属和许可证。
3. 在 `allow-git` 中精确允许仓库 URL。
4. 依赖必须使用完整提交 `rev`，不能跟踪分支或标签。
5. 上游发布可用 crates.io 版本后应移除例外。

## 7. 文件和职责

### 7.1 `deny.toml`

保存机器可执行规则：

- 全局许可证白名单。
- 按包许可证例外。
- 许可证文本推断置信阈值。
- 注册表和 Git 来源规则。

配置中的注释使用中文，只解释本项目决策，不复制大段上游模板。

### 7.2 `docs/dependency-license-policy.md`

保存长期规则：

- 许可证分级。
- Cargo 与非 Cargo 组件边界。
- 新增依赖审查流程。
- 条件例外必须记录的信息。
- 发布阶段仍需完成的归属和源码义务。

### 7.3 `scripts/verify-licenses.ps1`

职责：

1. 查找 `cargo-deny`。
2. 精确校验版本为 `0.20.2`。
3. 缺失或版本错误时输出确定性的中文错误和安装命令。
4. 在仓库根目录执行：

```powershell
cargo deny --locked check licenses sources
```

脚本不得静默跳过检查，也不得自动修改全局开发环境。

### 7.4 `scripts/test-license-policy.ps1`

使用临时目录生成最小 Cargo 依赖图，验证：

- 允许许可证和 crates.io/路径来源能通过。
- `GPL-3.0-only` 路径依赖被拒绝。
- 未批准 Git 来源被拒绝。
- 负向用例必须因预期诊断失败，不能把“命令自身崩溃”误判为策略生效。

临时 Git 依赖由脚本本地创建并提交，不访问远端网络。测试结束后删除临时目录；删除前验证目录确实位于系统临时目录下。

### 7.5 `scripts/verify.ps1`

在 Rust 编译测试之前依次运行：

1. 文本编码检查。
2. 许可证策略负向测试。
3. 当前 workspace 的许可证和来源检查。

许可证门禁应尽早失败，避免违规依赖先消耗完整编译时间。

## 8. 错误处理

- 工具缺失：立即失败，说明固定安装命令。
- 工具版本不符：立即失败，同时显示期望版本和实际版本。
- 当前依赖图违规：保留 `cargo-deny` 原始诊断并让统一验证失败。
- 负向夹具意外通过：测试失败，说明对应规则没有生效。
- 负向夹具因元数据、Git 初始化或配置解析失败：测试失败，不算作成功拒绝。
- 临时目录清理失败：测试失败并保留路径，避免隐藏环境问题。

不通过捕获字符串后无条件返回成功来吞掉子进程错误。每个预期失败都必须同时校验退出码和目标诊断类别。

## 9. 自动化测试

### 9.1 配置负向测试

- 宽松许可证基线通过。
- `GPL-3.0-only` 产生许可证拒绝诊断。
- 本地 Git 依赖产生未知 Git 来源诊断。
- 未固定到完整 `rev` 的未来允许 Git 依赖仍被来源策略拒绝。

### 9.2 当前仓库检查

- 使用 `--locked`，确保审计对象与 `Cargo.lock` 一致。
- 检查普通依赖和开发依赖。
- 检查 workspace 当前解析到的全部目标依赖。

### 9.3 完整回归

运行：

```powershell
.\scripts\verify.ps1
```

必须继续通过 UTF-8、格式、全 workspace 测试、Clippy、Rust 文档和 Git 差异检查。

本项没有必须人工执行的验收。

## 10. 已知边界

`cargo-deny` 依赖 crate 元数据和可识别的许可证文件，不会穷举检查每个源码文件，也不能自动证明二进制发布已经满足所有归属、源码或重新链接义务。

因此：

- 机器门禁负责阻止未经批准的 Cargo 许可证和来源。
- 中文策略文档负责记录项目接受条件。
- 具体弱 copyleft 依赖 issue 负责记录链接和分发方案。
- 发布阶段负责生成并核对最终第三方清单、许可证文本和源码获取说明。

这四层不能互相替代。

## 11. 实施顺序

1. 先写会失败的策略负向测试。
2. 增加 `deny.toml`，让许可证和来源夹具按预期通过或失败。
3. 增加固定版本检查和 workspace 审计脚本。
4. 接入统一验证入口。
5. 回写中文策略、README 和粗粒度阶段状态。
6. 完整本地验证、自审、提交 PR 并合并。
