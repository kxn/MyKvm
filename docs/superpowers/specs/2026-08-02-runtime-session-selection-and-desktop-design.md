# 运行时设备选择与桌面版本设计

- 关联 issue：#32（headless HTTP 管理 API）、#33（桌面 app）
- 日期：2026-08-02
- 状态：设计修订，替代“启动时命令行固定设备”的产品假设

## 背景

KVM 软件的核心体验不是“启动进程时把设备写死”，而是用户打开控制入口后能看到设备列表、选择相机和串口、开始会话，并在选错设备时切换。当前 `headless` 已有 CLI/TOML 配置，但这只能作为默认值和无人值守部署入口，不能替代运行时选择。

本轮设计把“选择设备”作为产品能力，而不是传输层能力。浏览器入口、后续桌面入口都调用同一套会话组装逻辑；RFB TCP/WS 只是消费当前会话的帧源与输入事件通道。

## 结论

采用“运行时会话重启”模型：

- API 和桌面 UI 都支持运行时选择 `video` 与 `serial`。
- 内部实现先停止并销毁旧会话，释放旧帧源和串口 sink 后，再构造新帧源、新输入 sink、新输入泵。
- 监听端口、HTTP 服务、TCP/WS 传输服务不重启。
- 已连接的 RFB 客户端不承诺无缝热替换；切换设备时旧事件通道关闭，旧连接断开并释放连接闸门，新连接可重连到新会话。
- 不做真正的帧源无缝热替换、不中断连接的 framebuffer 切换、强踢客户端协议扩展。

这满足用户“选错设备可以 live 换”的产品需求，同时避免把后端设计成全动态热插拔系统。

## 可选方案与取舍

### 方案 A：启动参数固定设备

实现简单，但用户选错设备只能重启进程。这个方案只适合作为默认配置，不适合作为产品交互模型。

### 方案 B：会话级重启（采用）

运行时请求携带新设备选择，后端停止旧会话、释放旧资源、创建新会话、发布新的帧源和输入事件通道。传输层继续监听，新连接拿到新会话；旧连接自然断开或在旧事件通道关闭后结束。复杂度集中在会话边界，容易测试和维护。

### 方案 C：真正无缝热替换

旧 RFB 连接不断线，内部动态切换帧源和输入 sink，并处理分辨率、像素格式、输入坐标 epoch、串口释放和客户端状态迁移。这是后续增强，不适合当前最小产品化阶段。

## Headless 设计

### HTTP API

- `GET /api/devices`：返回视频设备和串口设备列表。
- `POST /api/session`：
  - `{"action":"restart","video":"<device-id>","serial":"COM9"}`：按请求设备启动新会话；缺省字段沿用上一成功会话选择；初始选择来自启动配置；`serial` 为空字符串表示无真实串口、使用模拟队列。
  - `{"action":"create", ...}`：仅无会话时首启。
  - `{"action":"stop"}`：停止当前输入泵并释放输入状态。
- `GET /api/status`：返回服务、当前视频源、最近帧、控制连接、会话状态、输入统计、丢帧计数、串口统计。
- `GET /api/screenshot`：基于当前帧源返回 JPEG。

全部 API 走同一套 HTTP 鉴权：配置 `[auth] token` 时要求凭证，未配置时不鉴权、任意来源匿名放行（#95 起为显式启用语义，替代旧的回环回退）。

### 会话组装边界

`SessionFactory` 负责把一次设备选择转换为 `(Arc<dyn FrameSource>, InputSink)`。它持有启动配置作为默认值；请求中的 `video`/`serial` 只覆盖对应字段，未给出的字段沿用上一成功选择。

`SessionManager` 负责会话生命周期：

- `create`：无会话时创建会话结构。
- `stop_and_destroy`：停止旧会话（如有）、等待旧输入泵释放、销毁旧帧源和 sink，供独占设备重新打开。
- `create` + `start`：按新设备选择组装并启动新输入泵。
- `replace_and_start`：保留给已预先构建好新组件的内部替换场景；运行时真实设备切换优先使用 `stop_and_destroy` 释放旧资源后再构建。
- `stop`：停止输入泵，但保留当前已选择的帧源用于状态和截图。

`restart` 的失败语义（历史）：新设备构建失败时，后端尝试按上一成功选择重新构建会话并启动；若回滚成功，请求仍返回 `500` 告知本次切换失败，但系统回到上一会话选择。若回滚也失败，会话保持空状态并返回包含回滚失败原因的 `500`。

此失败语义已被 #55 更新：video/control 构建失败进入共享 `SessionSupervisor`
的 `Recovering/Failed` 状态，HTTP create/restart 和 desktop connect 不再因为
单条设备链路打开失败而自动回连接页或按上一选择回滚。人工 stop 仍是明确停止路径。

### 当前帧源发布

传输层不缓存启动时帧源。本文最初设计中，headless 曾维护 `SwitchableFrameSource`：

- `latest_frame()`、`source_info()` 委托给当前帧源。
- `subscribe()` 在新连接建立时订阅当前帧源。
- 会话切换前临时切到空帧源以释放旧独占资源；新会话启动成功后更新为新帧源。

此模型已被 #55 取代：当前长期模型是 `ipkvm-session::FrameHub`。RFB、headless
截图和 desktop 主画面都订阅稳定 hub；底层视频源替换不会关闭上层订阅。旧事件
通道关闭也不再作为观看连接结束条件，控制不可用时 RFB 进入只读输入语义。

## Desktop 设计

桌面 app 不依赖 `headless`，只依赖 `ipkvm-session`、`ipkvm-core`、`ipkvm-video`。

第一版桌面 UI 是工具型应用，不做营销页：

- 顶部工具栏：视频设备下拉、串口设备下拉、刷新设备、连接/重启、停止。
- 主区域：当前帧显示；无帧时显示“无信号”。
- 状态栏：会话状态、输入事件数、最后输入时间、丢帧、当前控制来源。

内部同样采用会话级重启：

- 设备选择变更后点击连接/重启。
- winit 键盘/鼠标事件转换为内存 `RfbServerEvent`。
- `RfbInputPump` 消费内存事件，驱动 `Ch9329InputSink`。
- 无 HTTP、无 token、无 TCP/WS 监听端口；安全边界是本机可信环境。

桌面渲染第一版只要求 BGRA8888 直接显示。YUY2/NV12 shader、无缝设备热替换、多窗口、多查看者留后续。

## 错误处理

- 设备枚举失败：`503` + `{error, detail}`。
- 会话构建失败（#55 后）：video/control 构建错误进入 supervisor 恢复状态；`create/restart`
  返回当前会话状态，状态详情通过 `/api/status.video.runtime` 与
  `/api/status.session.control` 暴露。请求格式错误、未知 action、已存在冲突仍按
  HTTP 错误返回。
- 会话已存在时 `create`：`409`。
- 未知 action：`400`。
- 未鉴权：沿用现有鉴权响应。

## 测试策略

- 管理 API 集成测试覆盖：设备列表、按 `video` 重启后 status/screenshot 使用新帧源、未知 action、鉴权拒绝。
- 会话管理单元测试覆盖：空会话首启、运行中替换并启动、停止状态替换并启动、重复 create 冲突。
- 传输集成测试覆盖：会话重启后新 RFB 连接使用新帧源尺寸；活动 TCP/WS 连接期间重启不会毒化 gate，旧连接断开后新连接能成功握手。
- 资源生命周期测试覆盖：运行时重启必须先释放旧帧源/sink，再调用工厂打开新独占资源。
- browser fixture 回归测试必须恢复：`READY`、`STOPPED`、stdin EOF 都稳定。
- 完成前运行 `cargo fmt --all --check`、`cargo test --workspace --all-features`，最终再跑 `scripts/verify.ps1`。

## 自审

- 无占位需求；不承诺无缝热替换。
- `headless` 和 `desktop` 共享会话重启模型，但不共享 HTTP 栈。
- CLI/TOML 仍是默认配置，不再是唯一设备选择入口。
- `/api/session` 支持设备字段，不再用 501 回避核心需求。
- 本设计主动接受切换时旧连接断开，以换取独占设备释放顺序清晰、实现可维护。
