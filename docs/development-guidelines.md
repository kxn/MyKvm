# 开发规范

本文定义 my_ipkvm 的日常开发规则。目标是让每次改动都能追溯到明确问题、尽量由自动化验证，并把长期结论沉淀到文档中。

## 基本原则

- 所有仓库内自写文档使用中文。
- 非平凡工作以 Gitea issue 为入口。
- 默认优先自动化测试，人工验证只作为无法稳定自动化时的例外。
- 代码修改优先从根因修复，禁止用临时绕过代替真实修复。
- 设计结论、协议约定和开发规则一旦确定，应写入长期文档，而不是只留在 issue 讨论里。

## 文档语言

仓库内由项目维护者编写的文档必须使用中文，包括：

- `README.md`。
- `docs/` 下的设计、计划、审查、规范和说明文档。
- `.gitea/` 下的 issue 模板和 PR 模板。
- `AGENTS.md`。

以下内容可以保留原文：

- 外部协议、标准、库文档和许可证。
- 代码标识符、命令、文件路径、协议字段和第三方专有名词。
- 引用外部资料时的短摘录。

外部资料进入 `docs/references/` 时，必须在中文索引或中文说明中写清楚用途、来源和许可证边界。

## Issue 驱动开发

issue 是一次工作的工作单元，记录过程事实；长期文档记录项目长期事实。

需要开 issue 的情况：

- 新功能。
- bug 修复。
- 架构、协议、模块边界或依赖策略调整。
- 测试策略、开发流程或 CI 规则调整。
- 需要硬件或人工验证的问题。

可以不开 issue 的情况：

- 只修正错别字、格式、链接。
- 不改变含义的文档微调。
- 本地实验且不提交到仓库。

每个开发 issue 至少包含：

- 背景和问题。
- 目标和不做范围。
- 验收标准。
- 自动化测试计划。
- 人工验证例外，如果没有则写“无”。
- 相关文档。

分支、提交和 PR 应使用 `#编号` 关联 issue。PR 合并时使用 `Closes #编号` 或等价关键字收口。

## Issue 与文档的关系

issue 和文档的职责分开：

- issue 记录一次工作的原因、讨论、取舍、验证和状态。
- 文档记录稳定的设计结论、协议契约、开发规则和用户可依赖的行为。

只改 issue 不改文档的情况：

- 实现细节不影响架构、协议、用户行为和后续开发方式。
- 讨论结论只对当前任务有效。

必须改文档的情况：

- 接口契约变化。
- 模块依赖方向变化。
- 视频、输入、RFB、串口等协议行为变化。
- 用户操作流程变化。
- 测试策略、开发规范或 CI 规则变化。
- 人工验证发现了硬件兼容性限制。

PR 描述必须说明是否修改文档。如果不修改文档，应写明原因。

## 自动化测试优先

默认要求每个改动都有自动化验证。优先级如下：

1. 单元测试：协议帧、状态机、坐标换算、配置选择、错误处理。
2. 集成测试：mock 视频源、fake serial、RFB 协议样例、headless 闭环。
3. 命令级验证：`cargo fmt --all --check`、`cargo test --workspace --all-features`。
4. 人工验证：真实采集卡、真实 CH9329/CH340 线、BIOS 行为、操作系统全局快捷键、真实 VNC 客户端兼容性。

人工验证只有在满足以下条件时才允许作为主要证据：

- 自动化环境无法稳定复现。
- 依赖真实硬件、驱动、固件、桌面系统权限或第三方客户端行为。
- issue 或 PR 中写明验证步骤、预期结果和实际结果。
- 能自动化的部分已经自动化。

如果一个人工验证场景后续可以自动化，应开独立 issue 跟踪。

## 根因修复

bug 修复必须优先定位根因。修复说明至少回答：

- 失败路径是什么。
- 根因在哪个模块或契约。
- 为什么这个修复能阻断同类问题。
- 哪个测试覆盖了回归。

禁止把以下做法作为最终修复：

- 固定延时掩盖竞态。
- 吞掉错误或只打印日志。
- 绕过类型系统和状态机。
- 只修改测试来适配错误行为。
- 在调用端到处补特殊分支，而不修正共享抽象。
- 无说明地降低功能或删除校验。

如果必须临时降级，应在 issue 和 PR 中写清楚原因、影响范围、退出条件和后续工作。

## 设计与计划

较大改动应先有设计或计划。判断标准：

- 涉及多个 crate。
- 改变公共 trait、协议帧、配置结构或数据模型。
- 会影响桌面版、headless 版、RFB/Web 入口中的两个或更多入口。
- 需要引入新依赖。
- 需要真实硬件验证。

设计文档写长期决策，计划文档写执行步骤。计划执行完后，若结论改变，应回写设计文档。

## PR 要求

PR 描述必须包含：

- 关联 issue。
- 改动摘要。
- 根因或设计依据。
- 测试命令和结果。
- 文档影响。
- 人工验证例外。

合并前最低检查：

```powershell
cargo fmt --all --check
cargo test --workspace --all-features
```

如果改动不涉及 Rust 代码，也应运行适合范围的检查，例如 Markdown 冲突标记扫描或模板渲染检查。

## Gitea 平台约定

本仓库使用 Gitea issue 和 PR 模板。Gitea 支持仓库内 issue/PR 模板，也支持在 issue、PR、commit 中使用 `#编号` 自动链接引用。
